# VLLの退勤日報（売上・バック発生商品）

**決定日**: 2026-11-22 ／ **判断**: 高野 ／ **ブランチ**: `feature/daily-report`（起点 `c092122` = 本番に出ているコミット。`origin/main` は `680800c` で止まっていて本番より古い）／ **本番**: 2026-11-22 11:50頃 反映（VLLの設定はオフのまま）

## なぜ

VLLのキャストに、退勤のときに売上（お客様名と金額）とバック発生商品（商品名・単価・個数）を書いてもらい、管理画面で集計したい（高野 2026-11-22）。
完成イメージ: https://claude.ai/artifact/SaiMYr43wjXXGajJYaRm3a （高野「それで良い」）

## 決めたこと（要件レビュー）

- 店舗設定 `requireDailyReport` をオンにした店舗だけ。既定オフで、星狼・stagegate は従来どおり
- 日報は必須。売上なしの日は「今日は売上なし」で退勤
- 売上は**お客様の会計を、ついたキャストのうち1人が書く**運用（高野）。2人とも書いたときに備える:
  - 入力時に「○○さんが同じお客様を書いています」と知らせる
  - それでも両方入ったら「重複の疑い」として管理画面に出し、店長が採用 / 別会計 / 取り消しを決める。決めるまでは金額が大きい方の日報だけを店の売上に数える
  - 日報の行は消さない（入れる時点で重複を消すと、誰が書いたか・判定違いが戻せないため）
- お客様の名前の表記ゆれは店舗ごとのお客様台帳（`customers`）で吸収。自動（敬称・カナ・全半角・空白）＋候補を店長がまとめる。まとめは1段で、分けられる
- 商品名は自由入力＋店舗設定の「よく出る商品」ボタン。バック率をかけた支払額は出さない（給与とはつながない）
- キャストは提出後に直せない。店長の修正画面は今回は作っていない

## 何を変えたか

- DB: `stores.requireDailyReport` / `stores.dailyReportProducts`、新テーブル `customers` / `daily_reports` / `daily_report_sales` / `daily_report_back_items`、enum `SaleDuplicateDecision`。`schema.sql` / `migrations.sql`（冪等）/ `schema.prisma`。日報→勤怠・スタッフは `Restrict`
- `lib/business/daily-report.ts`: 照合キー・似た名前・重複の数え方・集計（純粋関数）
- `actions/attendance.ts` `clockAction`: 日報が要る店舗の退勤は日報を検証し、退勤と同じトランザクションで保存。お客様の find-or-create はトランザクションの外（一意制約違反は読み直し）。退勤の二度押しは `daily_reports.attendanceId` の一意制約で1件に
- `actions/daily-report.ts`: 同じ日の同じお客様の確認（打刻URL＋PINセッション）/ 重複の判断 / まとめる・分ける / 日報の設定（専用の経路。`updateStore` からは2項目を落とす）。すべて監査ログ
- 打刻画面: 退勤で日報の全画面フォーム（`daily-report-form.tsx`）。書きかけは sessionStorage。PINセッション（5分）切れはPIN入力へ戻し、戻ると書きかけが復元される。完了画面に合計
- 管理画面: `/daily-reports`（要約・重複の疑い・5つの集計）と `/daily-reports/customers`（名前をまとめる）。サイドバーの「日報」は日報を使う店舗がある組織だけ。店舗詳細に「退勤の日報」の設定

## 確認

- 単体 236件（新規 `tests/unit/daily-report.test.ts` 31件）
- 実DB統合 18件（新規 `tests/integration/daily-report.db.test.ts` 10件）: 日報なしの退勤を弾く / オフの店舗は従来どおり / 表記ゆれの自動紐づけ / 同じ日の知らせ（自分の分は出ない）/ 重複の採用・取り消し / 重複でない組は判断不可 / まとめ1段・分ける / 設定は専用経路だけ / 退勤の二度押しで日報1件。**multi-clock-in と同じ店舗を使うので `--no-file-parallelism` で流す**
- 移行: デプロイ中のコミット（`c092122`）の `schema.sql`＋`migrations.sql` のDBに新 `migrations.sql` を2回流してエラー0・テーブル35。新 `schema.sql` だけの新規DBも通る
- `next build` が通る。本番ビルドを別ポート（3911）で起動し、Playwright で操作:
  - キャスト: 退勤→空で送るとエラー→「タケシ様」を入れると先に書いた2人の分が出る→行追加・商品ボタン（2回で個数2）→再読み込みしても書きかけが残る→送信→完了画面に合計 ¥17,000。ページのJSエラー0
  - 管理: サイドバーに「日報」/ 店の売上が重複を除いた額で出る / 「こちらを採用」で確かめること 1→0 / 名前の候補（「ゆうと（常連）」と「ユウト」）をまとめると 4人→3人。まとめた結果、同じ日の2人分が新しく重複の疑いになる（想定どおり）

## 気になっていること（未対応）

- 店長が日報を直す画面・「日報なし」の勤怠に後から日報を入れる画面は無い（一覧には「日報なし」と出る）
- CSV出力は無い
- 「日報なしの退勤」は、その店の最初の日報より後に退勤した勤怠を数えている（設定をオンにした日時を持っていないため）
- 打刻画面のお客様の候補は、その店のお客様（代表）を新しい順に500件まで。共用端末でほかのキャストにも見える
- ローカルの `node_modules` の next が 16.2.10 だった（`680800c` で 16.4.3 に上げたはず）。本番イメージは lockfile で入るので影響は無いはずだが、ビルド前に `npm ci` する
- `clock-session.ts` の `AUTH_SECRET` に既定値のフォールバックがある（既存。グローバルの方針では本番は例外にすべき）

- サーバーではビルドしない。ローカルでイメージを作って `docker save | ssh docker load`（2026-10-27 と同じ手順）
- 反映後、VLLの店舗詳細で「退勤のときに日報を書いてもらう」をオンにし、よく出る商品と単価を入れる（単価は高野かしのに確認）
- オンにした時点から、キャストは日報なしで退勤できなくなる。キャストへの周知が先

## 本番反映（2026-11-22）

- 反映前: available 589MB / 勤怠 2,384件
- バックアップ: `/home/ubuntu/backups/misekin/misekin-20261122-pre-dailyreport.sql.gz`（勤怠 2,384行入りを確認）
- コミットから切った一時 worktree でローカル `docker build` → `misekin-app:dailyreport-20261122`（`.env` が入っていないことを確認）→ `docker save | gzip | ssh docker load`（18秒）→ `latest` に付け替え → `docker compose up -d --no-build --no-deps app`。サーバー上ではビルドしていない
- 起動時の migrations.sql: 日報の4テーブル・2列・enum・FK を確認（日報→勤怠・スタッフは RESTRICT）。全8店舗の `requireDailyReport` は false。勤怠は 2,384件のまま
- エラー1件は既存: `migrations.sql:89` の旧一意インデックス `shift_availabilities_staffId_storeId_businessDate_key`。シフト希望が時間帯ごと（slotId 込みの一意制約）になってから、1日に複数の時間帯のデータがあり毎回失敗している。ON_ERROR_STOP=0 なので後続は流れる。今回とは無関係。消すなら migrations.sql のその行を削る（未対応）
- 外形: `/login` 200 / `/api/v1/attendance` キーなし 401 / `/daily-reports` 未ログインで 307 / VLLの打刻URL 200。アプリログにエラーなし
- 戻すとき: `docker tag misekin-app:corrscope-20261113 misekin-app:latest` → `docker compose up -d --no-build --no-deps app`。旧コードは新しいテーブルを読まないのでそのまま動く。日報が入ったあとに戻しても、日報のデータは残る
- まだやっていないこと: VLLの店舗詳細で日報をオンにする・よく出る商品の登録（商品と単価が決まってから）。キャストへの周知が先

## 追加: どこの店の分か（池袋 / 札幌）（2026-11-22）

- 高野「日報に選ぶところ足すだけで大丈夫。VLLは現地行くわけじゃないから統一で」。札幌店を別店舗にして勤怠・時給・打刻URLを分ける案（FC精算の人件費を分けられる）は採らなかった
- 店舗設定 `dailyReportLocations`（[string]）を足し、2つ以上なら日報の一番上で店を1つ選ぶ。サーバーで設定にある店か確かめ、`daily_reports.location` に保存。管理画面に「店ごと」（日報件数・重複を除いた店の売上・お客様数・バック対象）、一覧に店のタグ
- 最初は行ごとに選ぶ形で作ったが、高野「店は1つだけしか入れられないようにする」で日報ごとに1つへ変えた（本番に出す前なので、行の列は作っていない）
- 気になること: 札幌FCの精算（売上 − 決済手数料 − **札幌のキャスト人件費** − 15%）の人件費は、勤怠を分けていないので出せない。売上は日報の店ごとで出せる
- 確認: 単体 241件 / 実DB統合 20件（店が要る・設定外の店を弾く・保存・選ばせない店舗は null・通常の店舗編集から変えられない）/ 本番の `schema.sql`＋`migrations.sql`（`acb3588`）に新 `migrations.sql` を2回流してエラー0、新 `schema.sql` だけの新規DBも通る / `next build` / 本番ビルド（3911）で Playwright: 店を選ばずに送るとエラー、再読み込みで選んだ店が残る、送信→管理画面の店ごとが 札幌 3件 ¥40,900（重複は大きい方の 8,400 を採用）・池袋 1件（売上なし）、一覧のタグ。JSエラー0
