## 0. 前提：stage gate と Exhale の取り違え

作業の初期に**7月のCSVがstage gateではなくExhaleのものだった**ことが判明し、これが
「従業員バック対象のメニューがありません」の真因だった。切り分けに使った materials:

| | stage gate | Exhale |
|---|---|---|
| レジID | `0018` / `0020` | `0002` |

**レジ担当者名と、みせ勤の店舗別スタッフ登録を突き合わせると確実に判別できる。**

## 1. みせ勤APIの店舗スコープを stage gate だけに絞った

会計アプリが組織配下の全店舗の勤怠を取得していた。

- **`storeScope` を stage gate だけに設定した新しいAPIキーを発行**し、全店舗が見えていた
  旧キー「テスト利用」を失効。`storeScope` は**キー作成時のみ設定可**（編集UIなし）なので、
  範囲を変えるときは再発行になる
- アクセスログ上、旧キーの利用は会計アプリ（`python-requests`）だけだったので失効の影響なし

### 見つかったバグ（`src/app/api/v1/attendance/route.ts`）— commit `69ca534`

`where` にスプレッドを重ねていたため、後に書いた条件が前を上書きしていた。

```ts
// 修正前：どちらも businessDate を上書きし合う
...(dateFrom && { businessDate: { gte: dateFrom } }),
...(dateTo   && { businessDate: { lte: dateTo } }),
...(storeScope && { storeId: { in: storeScope } }),   // storeId 指定を握りつぶす
```

1. `storeScope` があるとクライアントの `storeId` 指定が黙って消える
2. **`from` と `to` を両方渡すと `to` が `from` を上書きし、開始日フィルタが効かない**

②の実害が大きく、会計アプリは常に `from`/`to` を両方渡すため、
**「`to` 以前の全期間・全店舗」を取得していた**。Exhale 1390件（2025-02〜2026-06）と
stage gate 15件が混ざり、稼働日数の自動算出が7月分で約499日になっていた。
（請求書は手入力で上書きされていたため、発行済みの帳票に汚染はなかった）

`staff/route.ts` は同じ処理を正しく書けていた（スコープ外は403）ので、そちらに揃えた。

## 2. キャスト明細に時給・交通費を載せ、合計振込額まで出した

会計アプリ側。commit `47f5090` → `29f933f` → `875bc0c` → `64af0c3`。

- 「バック明細」タブを「**お支払い明細**」に拡張。`合計振込額 = 時給 + 交通費 + バック`
- バックが0でも勤怠があればテキストを出す（従来は「バック>0の人」しか対象にしていなかった）
- 片方が欠けている場合は本文末に注記を入れる（金額だけ見て誤解しないため）

### ハマった2点

**① タブをまたぐと計算が間に合わない**
勤怠取得が「時給計算」タブ内のボタン任せで、他タブの計算に間に合っていなかった。
→ **CSV計算と同じタイミング（タブを描く前）でまとめて取得**し、稼働日数（Datad請求書）と
時給の両方が同じ勤怠を見るようにした。時給計算タブはお支払い明細タブに統合。

**② `key` 付きウィジェットが古い内容を保持する**
明細を `st.text_area(..., key=...)` で描いていたため、Streamlitがウィジェット状態を保持し、
**あとから時給が入っても表示が更新されなかった**。①だけ直しても見た目が変わらない。
→ `st.code()` に変更（毎回描き直され、コピーボタンも付く）。

再現テストで確認した挙動:

| 実行 | 勤怠データ | 表示 |
|---|---|---|
| 1回目 | なし | バックのみ |
| 2回目 | あり | バックのみ（変わらない）← ②のバグ |
| 勤怠ありで初回描画 | あり | 時給あり（ロジック自体は正しい） |

**教訓: Streamlitで「毎回計算し直して表示する値」に `key` を付けない。**

## 3. 時給の正をみせ勤に一本化した

時給が会計アプリ側のハードコード（1000円）で、みせ勤の `wage_histories`（時給マスタ・履歴あり）と
二重管理だった。Exhale側は既にみせ勤で管理されていた。

- **みせ勤の勤怠APIに `hourlyWage`（その営業日に効いていた時給）を追加**（commit `f9f569c`）。
  交通費と同じく履歴から日付で引き当てる
- 有効期間の引き当てを `src/lib/business/effective-period.ts` に切り出し、交通費と時給で共通化
  （同じ勤怠に別期間の設定が効く食い違いを防ぐ）
- 会計アプリは時給入力欄の初期値にこれを使う。未登録の人は暫定値＋警告を出し、
  **そのまま確定しないようにした**
- 期中で時給が変わっている人には、履歴どおり日ごとに積み上げた正しい額を警告に併記
  （美紅のように時給が3回変わっている実例がある）

ゆん・ミツルの時給1400円を **2026-07-01から遡って**登録（`WAGE_HISTORY_CREATE` 2件）。

### 注意点

`wage_histories.effectiveFrom` は画面から入れるとUTC0時だが、**Exhaleの既存行は
「実績CSVからの取り込み」で 15:00（JST0時）で入っている**。引き当ては
`toISOString().slice(0,10)` なので、Exhale分は1日ズレる可能性がある。stage gate は影響なし。

## 4. 交通費を支払いに含めた

みせ勤の勤怠APIは `transportationAmount` を返していたのに、会計アプリが使っていなかった。

- **交通費は退勤済みに限らず全ての記録から集計する。** 「その日に来たか」で決まるお金なので、
  退勤を押し忘れた日も払う（みせ勤側の計算と揃えた）。この場合でも本人がテーブルから消えないようにした
- ゆんの交通費を **出勤1回356円・2026-07-01から**登録（ミツルは既存で800円）
- **みせ勤は月額（MONTHLY）の交通費が未対応で常に0を返す。** APIからは「設定なし」と
  「月額だが未対応」を区別できないため、画面のキャプションに明記した

## 5. 修正申請を承認しても実働時間が変わらなかった — commit `eb6d506`

「承認済みのはずが反映されていない」というFBから発覚。`reviewCorrectionRequest` の
既存勤怠更新パスが `clockInAt` / `clockOutAt` しか更新せず、**`workMinutes` を再計算していなかった**。
時刻は直るのに実働時間が申請前のまま残るので、**承認しても給与額が1円も動かない**。

| スタッフ | 承認後の打刻 | 実働（誤） | 実働（正） |
|---|---|---|---|
| ゆん | 7/24 19:30–23:30 | 232分 | 240分 |
| ミツル | 7/27 19:00–23:38 | 54分 | 278分 |

管理者修正（`correctAttendance`）は正しく再計算していたので、そちらに揃えた
（休憩を反映して `breakMinutes` / `workMinutes` / 異常判定 / ステータスを引き直す）。
営業日は打刻時に確定したものを動かさない方針も `correctAttendance` に合わせた。

### 「承認したのにPENDINGのまま」の別ケース

打刻付け忘れ申請の承認には**同じ日の勤怠が既にあると弾く二重登録防止ガード**がある
（`attendance.ts:711`）。既に別経路で勤怠が入っていたため、承認が通らずPENDINGのままだった。
今回は運用判断で、既存勤怠に申請内容を反映したうえで承認済みにした（申請と勤怠を
`attendanceId` で紐付け、修正履歴と監査ログを残す）。ガード自体は安全装置なので変えていない。

## 7. 「未指定」のSPドリンク

キャスト名は**メニュー名から抜き出す**仕組み（`src/utils.py` の `extract_cast_name`）。
「SPドリンク」「オリシャン」「遠隔」「SP」を除去した残りがキャスト名になるため、
**キャスト名の付いていない素の「SPドリンク」を打つと `未指定` になる**。

7/3・伝票「やま」の1取引・3本（税抜¥6,000／バック¥1,200）が該当。ゆんの分と確認できたので
CSVを直接修正した（メニュー名と種別１の両方。`種別１` はPOSがメニュー名を複製している列）。

**CSVを直すときの手順**（cp932・CRLF を壊さないため pandas で往復させない）:

1. 元ファイルを `〜.修正前バックアップ.csv` としてコピー
2. cp932でデコード → 対象の取引Noの行だけ列単位で置換 → cp932で書き戻す
3. **差分のある行番号を出して、意図した行だけが変わったことを確認する**

同じ修正を**2回**手でやっている（POSから取り直すと元に戻るため）。
恒久対策として「未指定が出たら警告し、画面で割り当て先を選べるようにする」を提案済み・未着手。

## 9. シフトの時間帯が9時間ずれる — commit `b22462c`

「店舗タブで設定した時間帯どおりにシフトが打ち込めない」というFBから発覚。

```ts
const start = new Date(`${businessDate}T${startTime}:00`);   // 修正前
```

タイムゾーンの付かない文字列は**サーバーのローカル時刻**として解釈される。
本番コンテナは `TZ` 未設定＝**UTC**。表示側は `toZonedTime(..., "Asia/Tokyo")` で
JSTに直すため、**19:00で設定した枠が翌日04:00と表示される**。

- `slotTimes()` を `src/lib/business/shift-slot-time.ts` に切り出し、**店舗の `timezone` で解釈**
  （勤怠の営業日計算と同じやり方に揃えた）。手動作成と自動生成の両方に適用
- 日跨ぎは「24時間足す」をやめ、翌日の日付で解釈し直す（夏時間対策）
- 時刻の検証を `00:00〜23:59` に厳格化。`^\d{2}:\d{2}$` だったため `24:00` も `99:99` も通っていた
- **サーバーTZを UTC / Asia/Tokyo / America/New_York に変えて全181件パス**することを確認
- 本番の `endTime='24:00'` の枠2件を `00:00` に正規化（`SHIFT_SLOT_REPLACE` 2件）

**教訓: 日付文字列を `new Date()` に渡すときは必ずタイムゾーンを明示する。
サーバーのTZ設定に結果が依存するコードは、テストでTZを変えて回すまで気づけない。**
