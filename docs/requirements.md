# 要件定義書 — みせ勤

## 1. プロダクト概要

**アプリ名**: みせ勤 (Miseki)
**対象**: 複数店舗を運営する小規模事業者・飲食店・コンカフェ・バーなど
**目的**: 深夜営業・日またぎ勤務・複数店舗所属に対応した継続運用可能な勤怠管理ツール

## 2. ステークホルダー

| 役割 | 説明 |
|------|------|
| 組織オーナー | 組織を作成した最初のユーザー。最高権限を持つ |
| 管理者 | オーナーから招待された管理者。店舗スコープを制限可能 |
| スタッフ | 勤怠記録の当事者。打刻と自分の勤怠確認が主な操作 |
| 外部システム | APIキーを使った外部連携システム |

## 3. 機能要件

### 3.1 認証・アカウント管理
- メールアドレス + パスワードによる登録・ログイン
- メールアドレス確認（メール送信）
- パスワード再設定（メール送信）
- セッション管理（httpOnly Cookie）
- 将来的にOAuth（Google等）追加可能な構造
- ログイン試行回数制限

### 3.2 組織管理
- ユーザーが最初に「組織」を作成する（UIは「お店・グループ」として表示可）
- 組織オーナーは1人以上必須（0人にならない制約）
- オーナーは自分が唯一のオーナーであれば権限を下げられない
- 複数組織への所属（組織切替機能）

### 3.3 店舗管理
- 組織内に複数店舗を作成
- 店舗ごとのタイムゾーン・営業日切替時刻を設定
- 店舗は物理削除せず無効化（過去勤怠との関連を保持）
- 店舗専用打刻URLの発行・再発行・無効化・有効期限設定
- QRコード表示

### 3.4 スタッフ管理
- スタッフはメール招待（招待→在籍の状態遷移）
- 1スタッフが複数店舗に所属可能
- 在籍状態：招待中 / 在籍 / 休職 / 退職 / 利用停止
- 物理削除不可
- 時給は適用期間付き履歴として管理（上書き不可）
- 交通費は店舗所属ごとに設定
- 打刻用PIN（ハッシュ保存）

### 3.5 打刻機能
- 店舗専用URLから管理者ログイン不要で打刻
- スタッフ選択 → PIN入力 → 打刻操作
- 状態遷移：未出勤 → 勤務中 → 休憩中 → 勤務中 → 退勤済み
- 店舗設定「同じ日に退勤後もう一度出勤できるようにする」がオンの店舗は、退勤済みから再出勤できる（同じ営業日の別の勤怠になる。確認ダイアログあり）。VLLの遠隔推し活（店舗勤務の退勤後に在宅で再出勤）のため。既定はオフ（2026-10-27）
- 不正な状態遷移は防止（UI + サーバー両方で検証）
- 休憩中退勤は確認ダイアログを表示し退勤時刻と同時刻で休憩終了を自動記録
- PIN連続失敗にレート制限
- 打刻後の完了画面（数秒後にスタッフ選択へ戻る）
- 共用端末考慮（他人の情報を画面に残さない）

### 3.5.1 退勤の日報（2026-11-22）
- 店舗設定「退勤のときに日報を書いてもらう」がオンの店舗（VLL）は、退勤ボタンで日報の画面が開き、日報を送ると同時に退勤する。日報なしでは退勤できない（サーバーでも検証）
- 売上: お客様名（自由記述）と金額を1行で入れる。行は追加・削除できる。同じお客様の売上は、ついたキャストのうち1人だけが書く運用
- バック発生商品: 商品名・単価・個数。店舗設定の「よく出る商品」はボタンで入る（単価も入り、その場で直せる）
- 売上がない日は「今日は売上なし」にチェックして退勤する（入れ忘れと区別する）
- 同じ店・同じ営業日に別のキャストが同じお客様（表記ゆれ込み）を書いていたら、入力欄の下に知らせる
- 書きかけは端末の sessionStorage に残す。PINのセッション（5分）が切れたらPIN入力に戻し、入れ直すと書きかけが戻る
- 提出後の修正はキャストからはできない（店長に伝える）。管理画面からの修正・日報の後入れは未実装
- 管理画面「日報」: 店舗・月ごとに、店の売上（重複を除く）/ バック対象合計 / 日報件数 / 確かめること（重複の疑い・日報なしの退勤）。キャスト別・商品別・お客様別・日別・日報一覧
- 重複の疑い（同じ日に2人以上が同じお客様の売上を書いた）は、店長が「こちらを採用」「別の会計なので両方数える」「取り消す」で決める。決めるまでは金額が大きい方の日報だけを数える。行は消さない
- お客様の名前の表記ゆれ: 敬称・カタカナ/ひらがな・全角半角・空白の違いは自動で同じ人。それ以外（括弧の中だけ違う・片方が含む・1文字違い）は候補として出し、店長がまとめる。まとめた名前は「分ける」で戻せる
- バック対象合計は「単価×個数」の合計で、バック率をかけた支払額ではない（給与計算とはつないでいない）
- どこの店の分か（2026-11-22 追加。VLLの池袋 / 札幌）: 店舗設定に店を2つ以上入れると、日報の一番上で店を1つ選ぶ（1つの日報に店は1つ。選ばないと送れない。サーバーでも検証）。管理画面に「店ごと」の集計と、一覧に店のタグが出る。**勤怠は分けない**（キャストは遠隔で、どちらの店にも同じ条件で出るため。高野）。設定が空の店舗は選ばせず、店は null で保存

### 3.6 勤怠管理
- 日またぎ勤務：勤務日は営業日切替時刻で決定（午前0時分割不可）
- 実打刻時刻の保全（上書き禁止）
- 異常検出：退勤漏れ、休憩終了漏れ、逆転時刻、長時間勤務、重複打刻、複数店舗同時勤務
- 管理者による勤怠修正（修正前値を保全、理由必須、監査ログ記録）
- スタッフによる修正申請（申請中 / 承認済 / 却下 / 取消）
- 締め処理・勤怠ロック

### 3.7 監査ログ
- 全重要操作を記録（編集・削除不可）
- 記録項目：操作者、日時、種別、対象、変更前後、理由、IP、UA

### 3.8 CSVエクスポート
- UTF-8 BOM付き、Excel文字化け対策
- 大量データでもストリーミング出力
- 出力時に監査ログ記録

### 3.9 外部REST API
- APIキー認証（発行時1回のみ表示、DBはハッシュ保存）
- 組織・店舗スコープ
- レート制限
- OpenAPI仕様書 + Swagger UI
- バージョニング（/api/v1/）

### 3.10 通知
- Web通知（アプリ内）
- メール通知
- 通知種別：招待、修正申請作成・承認・却下、退勤漏れ、長時間勤務、APIキー発行・無効化

#### 3.10.1 勤怠の異常（打刻漏れ）を本人に知らせる（2026-11-27 追加）

高野の指示（2026-11-27）「打刻漏れを本人にメールで知らせる機能は作ろう。10月までのやつは知らせなくて良い」による。実装は `src/lib/business/anomaly-alert.ts`（判定）と `src/lib/notifications/anomaly-alert-job.ts`（送信）。

**いつ**: 毎朝1回（9:00 JST を想定）。サーバーの crontab から `POST /api/cron/anomaly-alerts` を叩く（後述）。

**何を（対象の勤怠）**: 次をすべて満たす勤怠。
- 営業日が **2026-11-01 以降**（10月以前は知らせない。定数 `ANOMALY_ALERT_START_DATE`）、かつ店舗の「今日の営業日」より前（＝前日までに終わった営業日）
- 実行時点のデータで異常判定（`detectAnomalies`）をやり直して、知らせる異常が1つ以上ある。保存済みの `hasAnomaly` は退勤時にしか更新されず、退勤漏れの勤怠では false のまま残るため、保存値には頼らない
- 営業日が終わっているのに退勤が無い勤怠は、経過時間が24時間未満でも「退勤漏れ」として扱う（夜に出勤して翌朝9時の時点では24時間たっておらず、判定上は「長時間勤務」になってしまうため）
- 知らせる異常は `MISSING_CLOCK_OUT`（退勤漏れ）/ `MISSING_BREAK_END`（休憩終了漏れ）/ `CLOCK_OUT_BEFORE_CLOCK_IN`（退勤が出勤より前）/ `LONG_SHIFT`（12時間以上）。長時間勤務だけの勤怠は「時刻が正しければ対応不要」と添えて1回だけ知らせ、再送しない
- 修正申請が1件でもある（審査中・承認・却下。取り下げは除く）勤怠、管理者が修正した履歴（`attendance_corrections`）がある勤怠、締め済み（`isLocked`）の勤怠は対象外。本人が申請できない／既に人の目が入っているため

**誰に**: 勤怠のスタッフ本人のうち、次をすべて満たす人。
- スタッフのステータスが `ACTIVE`（招待中・休職・退職・停止は送らない）。退職日が過去日の人も送らない
- ログイン用アカウント（`staff.userId`）があり、その組織のメンバーとして有効（`organization_members.isActive`）。組織自体も有効
- 送り先はログイン用アカウントのメールアドレス（`users.email`）。`staff.email` は使わない（ログインして申請してもらう前提のため）

**どう**: スタッフ1人につき1日1通にまとめる。件名「【みせ勤】打刻の修正をお願いします（N件）」。本文に営業日・店舗・出勤/退勤時刻・異常の内容を並べ、各行と末尾に「修正を申請する」リンク（`/my-correction-requests/new?attendanceId=...`、末尾は `/my-correction-requests/new`）を付ける。
同時にアプリ内通知（`notifications`、種別 `ATTENDANCE_ANOMALY_DETECTED`）を1件作る。ベルの未読数に出る。

**二重送信の防ぎ方**: 送った勤怠ごとに `attendance_anomaly_notices`（`attendanceId` 一意）に記録する（初回送信日時・最終送信日時・回数・その時の異常）。
- 記録がある勤怠は送らない。ただし **初回から7日たっても未対応のまま（上の条件を満たしたまま）なら1回だけ再送** する（最大2回）。長時間勤務だけの勤怠は再送しない
- メール送信に失敗したスタッフの分は記録も通知も作らず、翌朝もう一度試す
- 同じ日に2回叩いても、1回目で記録が付くので2回目は何も送らない
- `?dryRun=1` を付けると、送らず・記録せずに対象一覧だけ返す（本番の初回確認用）

**定期実行の仕組み**: リポジトリに cron/スケジューラが無いため、外部から叩く API ＋ 秘密キーの形にした。
- `POST /api/cron/anomaly-alerts`、ヘッダ `Authorization: Bearer <CRON_SECRET>`。`CRON_SECRET` が未設定なら 503 で何もしない（既定値のフォールバックは置かない）
- 本番はホスト（prod-server）の crontab に `0 9 * * * curl -fsS -X POST -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:3003/dev/misekin/api/cron/anomaly-alerts` を置く（コンテナは 127.0.0.1:3003 で待ち受け。basePath 込み）。サーバーの時刻が UTC なら `0 0 * * *`

**未実装の案（オプション）: 管理者向けの店舗別一覧**
同じタイミングで、店舗ごとに「未対応の打刻漏れ一覧」を管理者（オーナー＋その店舗の担当管理者 `store_admins`）に1通送る案。
- 中身: 店舗名、スタッフ名・営業日・異常・本人に知らせた日（初回/再送）・本人のアカウント有無。アカウントが無い／メール未登録で本人に届かない人の分こそ管理者が拾う必要がある
- 送る条件: 未対応が1件以上ある店舗だけ。毎日送るとうるさいので「週1（月曜）」か「本人への再送（7日）でも未対応になった分だけ」に絞るのが候補
- 実装するなら同じジョブの後段に足し、送った記録は店舗×日付で持つ。必要になったら高野の判断で着手する

## 4. 非機能要件

### 4.1 セキュリティ
- OWASP Top 10 対策
- 全DBクエリで組織スコープを明示（IDOR防止）
- フロントエンドの表示制御だけでなくサーバー側で認可検証
- セキュアCookie（httpOnly, SameSite）
- 秘密情報は環境変数管理

### 4.2 パフォーマンス
- 勤怠一覧のページネーション
- 大量CSVのストリーミング
- Server Componentsを適切に使用

### 4.3 アクセシビリティ
- WCAG 2.2 AA相当
- セマンティックHTML
- キーボード操作
- aria属性
- コントラスト比
- reduced-motion対応

### 4.4 レスポンシブ
- PC（1280px+）：管理画面
- モバイル（390px〜）：打刻画面・スタッフ画面優先

## 5. データ保全原則
- 物理削除原則禁止
- 実打刻イベント上書き禁止
- 修正データと元データの分離
- DB制約とトランザクションの活用
- 二重送信防止（打刻の冪等性）

## 6. MVP範囲外（次フェーズ）
- シフト管理
- 有給休暇管理
- 給与明細発行
- 深夜・残業自動計算（データ構造は準備済み）
- 高度なダッシュボード・グラフ
- CSVインポート
- Webhook
- 位置情報打刻制限
- 外部サービス連携（LINE、Slack、マネーフォワード等）
